# CLAUDE.md

Контекст для Claude Code при работе с этим репозиторием.

## Что это

Изолированный support-чат сервис для vizaje-nica.com. Специально НЕ связан с legacy-кодом основного сайта (Laravel API + Next.js) — общается с ним максимум через встраиваемый `<script>` виджет, никакого шаринга кода/БД.

## Архитектурные решения (и почему)

- **Bun + Elysia, не NestJS** — сервис маленький (auth + chat + WS), Nest даёт лишний boilerplate без выгоды на таком масштабе.
- **Postgres, не MySQL** — хотя основной сайт на MySQL (Laravel), изоляция важнее унификации: это отдельный микросервис.
- **JWT с обязательным полем `type`** (`'visitor' | 'admin'`) — оба типа токенов подписаны одним `JWT_SECRET`, значит и widget-сессия, и admin-токен успешно проходят verify друг друга. Различать нужно ПО ПОЛЮ `type` в payload, а не по тому, какая функция верификации "не упала". Это реальный баг, который ловили — не убирать проверку `type`.
- **Токен посетителя — 30 дней**, хранится в localStorage виджета. Смена устройства = новая сессия, новый `conversationId` (сознательное решение, без linking по email/телефону — это отдельная фича на будущее).
- **Admin-токен — 12 часов** (было 15 минут, слишком раздражало).

## WebSocket — важные детали реализации

- Аутентификация на WS — **только через query-параметр** (`?token=...`), НЕ через заголовок `Authorization`: браузерный нативный `WebSocket` не умеет ставить кастомные заголовки на хендшейке. Postman это умеет, браузер — нет.
- `ws.publish(room, payload)` **не сериализует объект сам** (в отличие от `ws.send()`) — `payload` обязан быть уже `JSON.stringify(...)`. Забытый stringify — тихий баг: сообщение публикуется, но на клиенте `JSON.parse` в `onmessage` падает молча.
- `ws.publish(...)` **не отправляет отправителю** его же сообщение — только другим подписчикам комнаты. Клиент обязан рисовать своё сообщение optimistic-ом сразу при отправке, не дожидаясь WS.
- Комнаты: `conversation:{id}` (одна беседа) и `admin:global` (все операторы видят все новые сообщения для списка бесед).
- `connections` — обычная `Map<ws.id, ConnStore>` в памяти процесса, не через `ws.data` (мутация `ws.data.store` ненадёжна/недокументирована в Elysia).

## Тестирование

Предпочитаемый способ проверки WS-логики — `bun run src/scripts/test-realtime.ts`, а не ручное тестирование через браузерную консоль/Postman. Ручное тестирование через несколько F5 и разные вкладки создавало путаницу с "мёртвыми" WS-соединениями и протухшими токенами — автотест снял большинство таких ложных багов.

## Стиль работы

- Изменения показывать точечно (что и где менять), не переписывать файлы целиком, если не просят.
- Один шаг за раз, не заваливать план вперёд.
- Модульная структура (папка на функциональность), не плоские shared-папки.
