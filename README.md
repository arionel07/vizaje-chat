# vizaje-chat

Standalone support-chat сервис для vizaje-nica.com (Jivo/Intercom-style). Не связан с legacy-кодом сайта — подключается через `<script>` виджет.

## Стек

- **Runtime:** Bun
- **Framework:** Elysia
- **БД:** PostgreSQL + Drizzle ORM
- **Auth:** JWT (отдельно для admin-операторов и анонимных widget-сессий)
- **Realtime:** WebSocket (нативный, через Elysia `.ws()`)

## Структура монорепо

```
vizaje-chat-api/      — API + WebSocket (Bun, Elysia, Drizzle)
  src/
    auth/             — admin login, JWT создание/проверка
    chat/             — сообщения, беседы, статус, rate-limit, публикация в WS
    widget/           — анонимные widget-сессии
    db/               — Drizzle schema + client
    routes/           — HTTP/WS роуты по доменам
    scripts/          — разовые скрипты (create-admin, test-realtime)
    config.ts         — переменные окружения
    index.ts          — сборка приложения
vizaje-chat-admin/    — веб-админка операторов (Vite + React)
vizaje-chat-widget/   — виджет для сайта (widget.js) и тестовая страница
```

## Локальный запуск

Нужны [Bun](https://bun.com) и Docker (для Postgres).

### 1. API (порт 3001)

```bash
cd vizaje-chat-api
bun install

# Postgres в докере
docker run --name vizaje-chat-db -e POSTGRES_PASSWORD=dev -p 5433:5432 -d postgres:16

# переменные окружения
cp .env.example .env    # затем впишите JWT_SECRET

# применить схему (таблицы и индексы)
bunx drizzle-kit push

# создать первого админа
bun run src/scripts/create-admin.ts admin@example.com пароль

# запуск
bun run src/index.ts
```

Проверка: `curl localhost:3001/health` возвращает `{"status":"ok"}`.

### 2. Админка (порт 5173)

```bash
cd vizaje-chat-admin
bun install
cp .env.example .env    # необязательно: по умолчанию API на http://localhost:3001
bun run dev
```

**Оповещения о новых сообщениях.** При заходе в админку браузер один раз спросит разрешение
на уведомления (если пользователь уже ответил — повторно не спрашивает). Новое сообщение
посетителя: звук (кнопка-колонка в шапке списка бесед выключает его), а если вкладка
неактивна — ещё и системное уведомление браузера (клик по нему фокусирует вкладку и
открывает беседу), бейдж с числом непрочитанных бесед на favicon и в `<title>`. Работает
только по HTTPS или на `localhost` — так требует Notification API.

### 3. Виджет (порт 8080)

```bash
cd vizaje-chat-widget
bun run dev --port 8080    # порт по умолчанию 8080
```

Откройте `http://localhost:8080`. Адрес API задаётся атрибутом `data-api` на теге `<script>` в `index.html`. Для встраивания на сайт:

```html
<script src="https://your-cdn/widget.js" data-api="https://chat.example.com"></script>
```

Необязательные атрибуты тега `<script>`:

| Атрибут | По умолчанию | Что делает |
|---|---|---|
| `data-theme` | `auto` | `auto` — системная тема посетителя, либо `light` / `dark` |
| `data-title` / `data-title-ro` | `Поддержка Vizaje-Nica` / `Suport Vizaje-Nica` | Заголовок панели и превью |
| `data-agent` / `data-agent-ro` | `Поддержка` / `Suport` | Подпись сотрудника под сообщениями |
| `data-lang` | по `<html lang>` страницы | Явно задаёт язык виджета и диктовки (например, `ro-RO`); без атрибута определяется автоматически — см. «Два языка (RU/RO)» ниже |
| `data-greeting` / `data-greeting-ro` | «Привет! 👋 Чем мы можем помочь?» / «Salut! 👋 Cu ce vă putem ajuta?» | Приветствие в пустом чате |
| `data-subtitle` / `data-subtitle-ro` | «Наша команда также может помочь» / «Echipa noastră vă poate ajuta și ea» | Подзаголовок под заголовком в шапке панели |
| `data-quick-replies` / `data-quick-replies-ro` | — | Быстрые вопросы под приветствием через запятую, до 4 штук (запятую внутри вопроса использовать нельзя) |
| `data-privacy-url` | — | Ссылка на политику конфиденциальности; без неё строка под полем ввода не показывается |
| `data-privacy-text` / `data-privacy-text-ro` | «Политикой конфиденциальности» / «Politica de confidențialitate» | Текст ссылки в этой строке (вместе с `data-privacy-url`) |
| `data-proactive-message` / `data-proactive-message-ro` | — | Текст проактивного приглашения (см. соответствующий раздел ниже); без него (обоих вариантов) фича выключена |
| `data-position` | `bottom-right` | `bottom-right` или `bottom-left` |
| `data-z-index` | `999999` | `z-index` виджета |
| `data-offset-bottom` | `20` | Отступ снизу в px |
| `data-offset-right` / `data-offset-left` | `20` | Отступ от края в px; действует тот, что соответствует `data-position` |

**Приветствие и быстрые вопросы** — чисто фронтовый рендер: в БД не пишутся, в историю и аналитику не попадают и пропадают, как только в беседе появляется первое сообщение. Клик по кнопке отправляет её текст как обычное сообщение посетителя. Пример:

```html
<script src="widget.js" data-api="http://localhost:3001"
        data-greeting="Здравствуйте! Чем помочь?"
        data-quick-replies="Есть ли в наличии?,Сроки доставки,Как оформить возврат"
        data-position="bottom-left" data-offset-bottom="80"></script>
```

### Два языка (RU/RO)

Весь интерфейс виджета — кнопки, подписи, плейсхолдеры, сообщения об ошибках
диктовки и загрузки файлов — переведён на русский и румынский и переключается
автоматически: по умолчанию виджет смотрит на `<html lang>` страницы, на
которой он встроен (`ro*` → RO, иначе RU). Один и тот же `<script>` работает
одинаково на ru- и ro-страницах сайта, если у них разный `<html lang>` —
никакой ручной настройки под каждую не нужно.

`data-lang` переопределяет автоопределение явно (на случай, если сайт не
всегда верно проставляет `lang`, или нужен виджет не на языке страницы):

```html
<script src="widget.js" data-api="https://chat.vizaje-nica.com" data-lang="ro-RO"></script>
```

Настраиваемый текст (приветствие, подзаголовок, быстрые вопросы, заголовок,
подпись сотрудника, текст ссылки на политику конфиденциальности, проактивное
приглашение) можно задать отдельно для каждого языка через суффикс `-ro` у
соответствующего атрибута: на RO-странице сначала берётся `-ro`-вариант, если
его нет — обычный (RU) атрибут, и только потом — встроенный перевод по
умолчанию. Так сайт может указать RU-текст один раз, не заботясь о RO, пока
не понадобится — ничего не сломается, просто RO-посетитель увидит RU-текст
для этого конкретного поля.

```html
<script src="widget.js" data-api="https://chat.vizaje-nica.com"
        data-greeting="Привет! 👋 Чем мы можем помочь?"
        data-greeting-ro="Salut! 👋 Cu ce vă putem ajuta?"
        data-quick-replies="Есть ли в наличии?,Сроки доставки"
        data-quick-replies-ro="Este în stoc?,Termenul de livrare"></script>
```

**Оформление** смоделировано по образцу Intercom: чёрный круглый лаунчер (иконка сообщения ⇄ шеврон при открытии/закрытии — независимо от темы сайта), квадратный тайл-«логотип» с сеткой из точек в шапке, двухстрочный заголовок (жирное название + серый подзаголовок), меню «⋯» справа (пока в нём только «Скачать историю» — замена отдельной иконки скачивания), единообразно скруглённые пузыри сообщений без «хвостика», составное поле ввода (textarea сверху, иконки эмодзи/диктовки и круглая кнопка отправки в строке снизу, всё в одной скруглённой рамке).

Позиция и слой читаются один раз при загрузке скрипта.

**Диктовка.** В поле ввода есть кнопка микрофона: речь превращается в текст по ходу разговора. Распознавание выполняет сам браузер (Web Speech API), поэтому серверная часть не задействована, а кнопка показывается только там, где браузер это умеет (Chrome, Edge, Safari; в Firefox её нет). Аудио при этом передаётся на серверы Google или Apple, о чём пользователь предупреждается при первом включении. Нужен HTTPS (на `localhost` работает и так), а браузер попросит доступ к микрофону.

Возвращающийся посетитель подключается к чату в фоне, поэтому на кнопке появляется бейдж непрочитанных, а над ней превью нового сообщения. Новым посетителям сессия создаётся только когда они открывают чат.

## Переменные окружения

### API (`vizaje-chat-api/.env`, шаблон в `.env.example`)

| Переменная | Обязательна | По умолчанию | Что делает |
|---|---|---|---|
| `DATABASE_URL` | да | — | Строка подключения к PostgreSQL |
| `JWT_SECRET` | да | — | Секрет подписи JWT; без него сервер не стартует |
| `ALLOWED_ORIGINS` | нет | `http://localhost:5173,http://localhost:8080` | Origins для CORS через запятую. Добавьте сюда домен сайта с виджетом и домен админки |
| `TRUST_PROXY` | нет | `false` | `true`, если API за reverse proxy: IP клиента берётся из `X-Forwarded-For` (нужно для rate-limit) |
| `PORT` | нет | `3001` | Порт HTTP/WS сервера |
| `TELEGRAM_BOT_TOKEN` | нет | — | Токен бота от @BotFather. Без него `/telegram/webhook` принимает сообщения, но не может ответить |
| `TELEGRAM_WEBHOOK_SECRET` | нет | — | Секрет, которым Telegram подписывает запросы на `/telegram/webhook` (см. `setWebhook`) — без него вебхук открыт всем, кто узнает URL |

### Админка (`vizaje-chat-admin/.env`)

| Переменная | Обязательна | По умолчанию | Что делает |
|---|---|---|---|
| `VITE_API_URL` | нет | `http://localhost:3001` | Адрес API; адрес WebSocket строится из него. Подставляется при сборке |
| `VITE_DICTATION_LANG` | нет | `ru-RU` | Язык диктовки (речь в текст) |

## WebSocket-протокол

Подключение: `ws://host/ws?token=...` (токен посетителя или админа). Клиент → сервер:

| Сообщение | Кто | Что делает |
|---|---|---|
| `{ text, replyToId?, clientId?, lang? }` | посетитель | Сообщение в свою беседу; `replyToId` — ответ на сообщение (только из этой же беседы); `lang` (`ru`/`ro`, по умолчанию `ru`) — язык автоответа бота, если `text` точно совпал с триггером |
| `{ conversationId, text, replyToId?, clientId? }` | админ | Сообщение в беседу, в том числе ответ на сообщение |
| `{ type: 'typing', conversationId? }` | оба | «Печатает» (не сохраняется, не чаще раза в секунду) |

Сервер → клиент — обычные сообщения (`{ id, conversationId, sender, text, createdAt, replyToId, replyTo }`, где `replyTo` — цитата `{ id, sender, text }` до 200 символов или `null`) и служебные события с полем `type`:

| `type` | Кому | Поля |
|---|---|---|
| `sent` | отправителю | `clientId`, `id`, `conversationId`, `createdAt` — подтверждение, серверные id и время |
| `error` | отправителю | `error`, `clientId` — сообщение отклонено (валидация, лимит) |
| `typing` | собеседнику | `from` (`visitor` / `admin`), `conversationId` |
| `read` | собеседнику и админам | `by` (`visitor` / `admin`), `conversationId`, `at` — «прочитано» |

«Прочитано» считается по серверному времени: оператор отмечает беседу прочитанной (`POST /admin/conversations/:id/read`), посетитель — когда виджет открыт (`POST /widget/read`); виджет читает состояние через `GET /widget/state`.

## Операторы и назначение бесед

Несколько операторов делят одну очередь бесед и могут назначать их друг на друга:

- `GET /admin/operators` — список операторов (`id`, `email`) для дропдауна назначения.
- `PATCH /admin/conversations/:id/assignee` — назначить (`{ "assigneeId": 2 }`) или снять назначение (`{ "assigneeId": null }`); публикует системное сообщение («Беседа назначена на …» / «Назначение беседы снято») по WS, как при смене статуса.
- `GET /admin/conversations?assignee=me` — только мои беседы; `?assignee=unassigned` — только без назначения (сочетается с `status`/`unread`).
- `GET /admin/conversations/counts` — добавлено поле `mine`.

В админке: дропдаун «Назначить» в шапке чата, фильтр «Мои» в списке бесед, инициалы назначенного оператора — бейджем на аватаре в списке. Операторы по-прежнему создаются CLI-скриптом `create-admin.ts` — отдельного UI/эндпоинта для создания операторов нет.

## Поиск по беседам

`GET /admin/conversations?q=текст` — ищет по всей истории переписки (не только по превью последнего сообщения) и по `sessionId` беседы, регистронезависимо, через `ILIKE %текст%` (полнотекстовый поиск для текущего масштаба избыточен). Сочетается с `status`/`unread`/`assignee`. Спецсимволы `%` и `_` в запросе экранируются, поэтому не ведут себя как маска.

В админке — поле поиска над фильтрами в списке бесед, debounce 350 мс, крестик или стирание текста возвращают обычный список с текущим фильтром; при пустом результате — «Ничего не найдено».

## Рабочий график и офлайн-статус

Вне рабочих часов виджет честно говорит посетителю, что сейчас никто не онлайн, а не создаёт ложное ощущение мгновенного ответа. Часовой пояс фиксирован — `Europe/Chisinau`.

- `GET /widget/status` — публичный (без авторизации): `{ online, nextOnlineAt, scheduleSummary }`. `nextOnlineAt` — ISO-время следующего открытия (или `null`, если график выключен целиком); `scheduleSummary` — человекочитаемая строка вроде `Пн–Пт 09:00–18:00, Сб 10:00–14:00`, склеивающая подряд идущие дни с одинаковыми часами.
- `GET/PUT /admin/settings/schedule` — только для админа. Тело/ответ: `{ timezone: "Europe/Chisinau", days: { mon: { enabled, start, end }, ..., sun: {...} } }` (`start`/`end` — `"HH:MM"`). Хранится в новой таблице `settings` (простой key-value, `jsonb`), без графика по умолчанию использует Пн-Пт 09:00–18:00. `PUT` проверяет формат времени и что начало раньше конца, при ошибке — 422 с текстом.
- В виджете: баннер над сообщениями при открытии чата, если `online: false`; отправка сообщений не блокируется — сообщение просто ждёт оператора.
- В админке: значок шестерёнки в шапке списка бесед открывает страницу графика (чекбокс + два `<input type="time">` на каждый день недели).

## Сезонная тема виджета

- `GET/PUT /admin/settings/theme` — только для админа. Тело/ответ: `{ theme: "classic" | "winter" | "halloween" }`, хранится в той же таблице `settings` под ключом `widgetTheme`, по умолчанию `classic`. `PUT` с неизвестным значением — 422.
- `GET /widget/config` — публичный (без авторизации), виджет вызывает его при загрузке страницы: `{ theme }`.
- Список тем держится в одном месте (`WIDGET_THEMES` в `settings/service.ts` на бэкенде и в `lib/api.ts` в админке) — добавить `spring`/`summer` в будущем можно дописав строку туда и ярлык в `ThemeSettings.tsx`, без переделки механизма.
- В виджете: при `theme: "winter"` поверх панели (но не поверх кликов — `pointer-events: none`) рисуются 8 падающих снежинок, CSS-анимация (падение + покачивание + вращение, `linear infinite`, разная длительность и фаза на каждую), приглушённая прозрачность, цвет снежинок берётся из CSS-переменной `--snow-color`, разной для светлой и тёмной темы, чтобы не сливаться с фоном ни в одной из них.
- При `theme: "halloween"`: аватар (в шапке и в превью нового сообщения) подменяется на отдельную картинку (`public/vizi-halloween.jpg`, кот в шляпе ведьмы) — подмена в JS (`applyHalloweenTheme()`), а не CSS, потому что `<img src>` уже вставлен в разметку к моменту, когда приходит ответ `/widget/config`. За лентой сообщений — статичный узор (летучие мыши, тыквы, привидения, кот, искры), как фоновые обои в Telegram: инлайновый SVG-тайл 160×160 в виде `background-image` на `.messages` (без `background-attachment` — по умолчанию узор неподвижен, а сообщения прокручиваются поверх него). Кнопка отправки и верхняя линия поля ввода — оранжевые (`#cd5f14`), оба правила — чистый CSS по классу `.root.halloween`, добавляемому в `applyHalloweenTheme()`. При `classic` — эффектов нет.
- В админке: вкладка «Тема виджета» в настройках — выпадающий список + кнопка «Сохранить», по образцу вкладки рабочего графика.

## Шаблоны ответов (RU/RO)

- Таблица `canned_responses`: `id`, `title` (язык-нейтральный заголовок для списка и поиска), `text_ru`, `text_ro`, `created_at`.
- `GET/POST/PATCH/DELETE /admin/canned-responses` — только для админа. `POST` и `PATCH` проверяют, что все поля непустые, иначе 422; `PATCH` частичный — поля, которых нет в теле, не трогает.
- В настройках (значок шестерёнки → вкладка «Шаблоны ответов») — список, создание/редактирование одной формой (заголовок + текст RU + текст RO), удаление.
- В `ChatWindow` — кнопка рядом с эмодзи открывает панель шаблонов: табы RU/RO (выбор языка запоминается в `localStorage` между сессиями), фильтр по заголовку на фронте, клик вставляет текст выбранного языка в позицию курсора, не отправляя — как вставка эмодзи.

## FAQ-бот с автоответами

- Таблица `bot_responses`: `id`, `trigger_text` (точный текст вопроса/quick-reply кнопки), `answer_ru`, `answer_ro`, `created_at`. Отдельная сущность от `canned_responses` — назначение разное: шаблоны вставляет оператор вручную, автоответы бот отправляет сам.
- `GET/POST/PATCH/DELETE /admin/bot-responses` — только для админа, та же схема валидации/ошибок, что у шаблонов ответов.
- В WS: когда посетитель отправляет сообщение, **точно** совпадающее с `trigger_text` одного из автоответов, сразу создаётся сообщение с `sender: 'bot'` и соответствующим `answer_ru`/`answer_ro` (по полю `lang` в сообщении посетителя) — без участия оператора. Не совпало — обычное сообщение ждёт оператора как раньше. Сообщения от админа триггер не проверяют. Эскалации на «позвать оператора» пока нет — добавится отдельным шагом при необходимости.
- Виджет передаёт `lang` в каждом сообщении (`ro`, если `data-lang` начинается с `ro`, иначе `ru`), поэтому клик по кнопке из `data-quick-replies`, чей текст совпадает с `trigger_text` в базе, даёт мгновенный автоответ бота вместо обычной отправки оператору — без отдельной логики на стороне виджета, кнопка просто шлёт текст как обычное сообщение.
- В настройках (значок шестерёнки → вкладка «Ответы бота») — список, создание/редактирование (триггер + ответ RU + ответ RO), удаление.
- В списке бесед и в окне чата сообщения от бота помечены иконкой робота (по аналогии с отрисовкой `sender: 'system'`).

## Экспорт переписки

- `GET /widget/export` (токен посетителя) и `GET /admin/conversations/:id/export` (токен админа, любая беседа по id) отдают всю историю беседы простым текстом: `Content-Type: text/plain; charset=utf-8`, `Content-Disposition: attachment; filename="conversation-{id}.txt"`.
- Формат: заголовок `Беседа #{id} — экспортировано {дата время}`, затем по одной строке на сообщение в хронологическом порядке — `[дата время] Отправитель: текст` (`Посетитель` / `Оператор` / `Бот`); системные сообщения (смена статуса, назначение) — отдельной строкой `--- текст ---` без таймштампа, как они есть в истории. Дата/время — в таймзоне `Europe/Chisinau`, как в рабочем графике.
- В виджете: иконка скачивания в шапке панели рядом с крестиком закрытия. В админке: кнопка-иконка в шапке `ChatWindow` рядом с «Назначить»/«Закрыть». Оба скачивают файл через `fetch` + `Blob` (эндпоинт требует авторизацию, прямая ссылка не сработает); имя файла берётся из `Content-Disposition`.

## Telegram как канал

Посетитель может писать боту в Telegram вместо виджета — для него это такая же
беседа, что видно в админке (список и шапка открытой беседы помечены иконкой
Telegram), и оператор отвечает из той же админки, не переключаясь в Telegram.

Перед тем как попасть к оператору, посетитель проходит меню на inline-кнопках
(`src/telegram/flow.ts`; само содержимое меню и состояние навигации — общие
с Instagram, см. ниже, в `src/channels/menu.ts` и `state.ts`):

```
/start (любой текст) → кнопка Start
  → приветствие + язык (RU/RO)
    → категория (Розница / Приложение / Сайт / Другое)
      → любая категория: «Опишите вашу проблему или вопрос» (с кнопкой Назад)
        → написанный текст — ВОТ ЕДИНСТВЕННОЕ место, где заводится беседа,
          сообщение уходит в админку, и посетитель сразу получает
          благодарность на своём языке («Спасибо! Передал оператору…»)
```
Перед самим вопросом оператору отдельным системным сообщением приходит
выбранная тема («Тема: Приложение»), всегда по-русски (на языке оператора,
а не посетителя), чтобы не переспрашивать, о чём вообще речь. Один раз за
заход в режим поддержки, а не на каждое сообщение — но заново при каждом
новом прохождении меню: беседа в Telegram одна навсегда (`chat.id`), и
человек может вернуться через время с другой проблемой, выбрав другую
категорию — тогда придёт новая тема, а не старая.

Благодарность после вопроса зависит от рабочего графика (тот же `settings`,
что у офлайн-баннера виджета, `GET/PUT /admin/settings/schedule`, по
умолчанию Пн–Пт 09:00–18:00 по Europe/Chisinau): в рабочее время — обычное
«Спасибо! Передал оператору, скоро ответит», вне графика — вместо этого
сообщаются часы работы («Сейчас мы не в сети. Обычно отвечаем в рабочие
часы: Пн–Пт 09:00–18:00»). Тоже один раз за заход, в тот же момент, что и
тема — повторные сообщения в том же заходе получают обычную благодарность,
без повтора часов.
На каждом экране — кнопка «Назад». Состояние навигации (язык/категория/шаг) —
в памяти процесса по `chat.id`, с префиксом канала (`src/channels/state.ts`,
ключ — `sessionIdForChat(chatId)`, то есть `telegram:<chatId>`, чтобы числовой
Telegram chat.id не столкнулся с таким же по значению Instagram-овым IGSID),
не в БД: это не переписка, а положение в меню, пропадёт только при рестарте
сервера, тогда человек просто снова жмёт Start.

Содержимое меню — обычные JS-объекты в `src/channels/menu.ts` (тексты и
подписи кнопок по языку/категории, общие для Telegram и Instagram),
редактируются без изменения логики.

После нажатия на кнопку её клавиатура сразу снимается тем же апдейтом
(`editMessageReplyMarkup`) — иначе старая кнопка под давно отправленным
сообщением Telegram остаётся кликабельной и может откатить навигацию назад.

- `POST /telegram/webhook` — сюда Telegram шлёт апдейты (`setWebhook`): обычные
  сообщения (`message`) и нажатия кнопок (`callback_query`). Беседа заводится
  (или находится по `chat.id`) только в момент, когда посетитель пишет текст
  после выбора категории — `channel: 'telegram'`, `sessionId: "telegram:<chatId>"`;
  дальше сохраняется и публикуется в WS ровно так же, как сообщение из виджета.
- Ответ оператора (WS, `store.type === 'admin'`) после обычного сохранения
  дополнительно отправляется в Telegram через Bot API — best-effort, ошибка
  отправки не блокирует ответ в самой админке.
- Без текста, без картинки и без `callback_query.data` (стикер, видео и т.п.)
  апдейт просто подтверждается `200 OK` и ничего не делает — иначе Telegram
  будет слать его повторно.
- Настройка: `TELEGRAM_BOT_TOKEN` + `TELEGRAM_WEBHOOK_SECRET` (см. переменные
  окружения выше) и регистрация вебхука — шаги в `deploy/DEPLOY.md`.

**Картинки.** Посетитель может прислать боту фото или картинку-файлом, пока он
в режиме «напишите вопрос» (вне этого режима изображение игнорируется — как и
обычный текст, просто перезапускает меню на Start). Бот скачивает файл через
Bot API (`getFile` → GET по `file_path`), сохраняет его как обычное вложение
(`src/uploads/service.ts`, тот же `/uploads/...`, те же ограничения по
типу/размеру) и доходит до админки как сообщение с вложением — ровно как
картинка из виджета. У сжатого фото (`message.photo`) Telegram не присылает
mime — угадывается по расширению в `file_path` (всегда JPEG); у
картинки-файла (`message.document`) mime берётся из `document.mime_type`.
Подпись к фото (`caption`) идёт как текст сообщения.

Ответ оператора с вложением дублируется в Telegram как `sendPhoto` — но
только если задан `PUBLIC_API_URL` (публичный адрес этого API, например
`https://chat.vizaje-nica.com`): Bot API сам скачивает картинку по ссылке,
относительный `/uploads/...` для этого не подходит. Без `PUBLIC_API_URL`
картинка в Telegram не дублируется, уходит только текст (если он есть) — это
единственное отличие от виджета, в остальном путь «вложение» одинаковый.

## Instagram как канал

Та же идея, что у Telegram, и то же меню (язык → тема → опишите вопрос,
`src/channels/menu.ts`/`state.ts` — общие с Telegram), но через Meta Graph
API (Instagram Messaging). Отличия чисто платформенные:

- Кнопки — [quick replies](https://developers.facebook.com/docs/messenger-platform/send-messages/quick-replies)
  вместо inline-кнопок: горизонтальный ряд под сообщением, до 20 символов на
  подпись. Instagram сам прячет их, как только собеседник ответил (текстом
  или другой quick reply) — свой аналог `clearTelegramKeyboard` не нужен,
  платформа уже решает проблему «старая кнопка осталась кликабельной».
- Нет команды `/start` — первое же сообщение от нового собеседника сразу
  открывает выбор языка (`src/instagram/flow.ts`, `showLanguage`), без
  отдельного стартового экрана.
- `POST /instagram/webhook` — та же структура апдейта, что у Meta Messenger
  Platform (`entry[].messaging[]`). Подписан HMAC-SHA256 от сырого тела на
  `INSTAGRAM_APP_SECRET` (заголовок `X-Hub-Signature-256`) — без секрета
  подпись не проверяется. `GET /instagram/webhook` — разовое рукопожатие при
  подключении вебхука в Meta-кабинете (`hub.verify_token` должен совпасть с
  `INSTAGRAM_VERIFY_TOKEN`, в ответ — `hub.challenge` как есть).
- Эхо собственных отправленных сообщений (`message.is_echo`) игнорируется —
  страховка на случай, если на странице включена подписка `message_echoes`
  (мы её не используем).
- Картинки — тот же путь, что у Telegram (ограничения по типу/размеру,
  `src/uploads/service.ts`), но скачивание в один шаг (вебхук сразу даёт
  публичный URL вложения, не нужен обходной `getFile`), а mime берётся из
  заголовка `Content-Type` ответа, не угадывается по расширению. Ответ
  оператора с картинкой уходит через Send API по `PUBLIC_API_URL` — тот же
  механизм и то же ограничение, что у Telegram: без `PUBLIC_API_URL`
  дублируется только текст. Подпись к картинке Send API не поддерживает —
  если она есть, уходит отдельным текстовым сообщением перед картинкой.
- Настройка: `INSTAGRAM_APP_SECRET` + `INSTAGRAM_PAGE_ACCESS_TOKEN` +
  `INSTAGRAM_VERIFY_TOKEN` (см. переменные окружения выше), подключение
  вебхука в Meta for Developers — шаги в `deploy/DEPLOY.md`.

## Проактивное приглашение (виджет)

Полностью фронтовая фича виджета, без бэкенда — отключена по умолчанию.

- `data-proactive-message` — текст приглашения; без него фича выключена.
- `data-proactive-delay` — задержка до показа, в секундах (по умолчанию 20).
- Пузырь всплывает рядом с кнопкой чата через заданную задержку, но только если чат ещё не открывали в этой вкладке и у посетителя нет `widget_token` в `localStorage` (то есть это анонимный визит, а не вернувшийся собеседник). Клик по тексту открывает панель чата; крестик закрывает пузырь и пишет флаг в `sessionStorage` — до конца текущей вкладки больше не покажется, в новой вкладке/сессии сработает заново.
- Использует тот же слот над кнопкой чата, что и превью нового сообщения (`.toast`) — одновременно они не показываются по построению (превью требует уже идущей беседы, приглашение — наоборот, её отсутствия), и учитывает `data-position`/`data-offset-*`.

## Удаление бесед

Выключено по умолчанию — `DELETE /admin/conversations/:id` отвечает `403`,
пока в Настройки → Опасная зона не включили переключатель (хранится как
обычная настройка, `settings.key = 'conversationDeleteEnabled'`). Включили —
в списке бесед (по наведению) и в шапке открытой беседы появляется иконка
корзины; удаление с подтверждением и необратимо (беседа и все её сообщения).
Рекомендуется включать точечно, на время чистки, и выключать обратно.

## Реакции на сообщения

Только для операторов — посетитель виджета их не видит и не ставит сам
(`GET /widget/messages` поле `reactions` не возвращает, только
`GET /admin/conversations/:id/messages`). 4 фиксированные реакции, не
настраиваются: ❤️ 👍 🔥 🙏 (`REACTION_EMOJIS`, `src/chat/reactions.ts`).

- `PUT /admin/messages/:id/reaction` — `{ emoji }`, ставит/заменяет реакцию
  текущего оператора на сообщении; `DELETE` того же пути — снимает. Один
  оператор — одна реакция на сообщение (`message_reactions`, unique по
  `(message_id, admin_id)`) — повторная простановка другого эмодзи заменяет
  прежний, а не добавляет вторую; два разных оператора могут поставить на
  одно сообщение разные реакции.
- Рассылка изменения — `admin:global` (не `conversation:{id}`: эту комнату
  слушает ещё и WS-подключение посетителя, а реакции ему знать не положено),
  `{ type: 'reaction', conversationId, messageId, reactions }` — с полным
  актуальным списком реакций сообщения, не дельтой.
- Фронт (`ChatWindow.tsx`): маленькая кнопка со смайлом у каждого сообщения
  (не только по наведению, как у «Ответить» — достижима на телефоне без
  долгого нажатия и работает при открытой клавиатуре), открывает пикер из 4
  эмодзи. Пикер рендерится порталом в `document.body` с `position: fixed` по
  координатам кнопки — иначе его обрезает `overflow-y-auto` списка сообщений
  у крайних (первых/последних) сообщений в беседе. Чтобы понимать, какая из
  реакций своя, `/admin/auth/me` теперь отдаёт ещё и `id` (раньше — только
  `email`).

## Push-уведомления в браузер админки (Web Push)

Отдельно от Expo push-уведомлений в мобильное приложение (`push_tokens`,
`push-tokens/`) — эти идут в сам браузер, в том числе на телефоне, причём
даже когда вкладка админки закрыта (на iOS Safari — только после
«Добавить на экран Домой», ограничение самого iOS: обычная вкладка там
Push API не поддерживает).

- `GET /admin/web-push/public-key` — публичный ключ VAPID-пары (не секрет,
  но за авторизацией, как и остальные `/admin/*`); `404`, если `VAPID_PUBLIC_KEY`
  не задан на сервере — фича просто выключена.
- `POST /admin/web-push/subscribe` / `POST /admin/web-push/unsubscribe` —
  сохранить/удалить подписку браузера (`{ endpoint, keys: { p256dh, auth } }`
  — то, что отдаёт `PushSubscription.toJSON()`). Таблица
  `web_push_subscriptions`: upsert по `endpoint` (один и тот же браузер на
  одном устройстве переезжает на нового оператора, если сменился владелец —
  тот же приём, что у `push_tokens`).
- Отправка — `src/web-push/send.ts`, вызывается из `ws.routes.ts` там же, где
  уже шлётся Expo push: на новое сообщение посетителя, всем сохранённым
  подпискам параллельно, best-effort (ошибка не блокирует обработку
  сообщения). `404`/`410` от push-сервера (подписка умерла — отписались,
  почистили данные браузера, переустановили) — тихо удаляем подписку из БД.
- Админка: `public/sw.js` — Service Worker, слушает `push` (показывает
  системное уведомление) и `notificationclick` (фокусирует открытую вкладку
  или открывает новую). `notifications/webpush.ts` — регистрирует его и
  оформляет подписку сразу после того, как получено обычное разрешение на
  уведомления (`ensureNotificationPermission` в `notifications/alerts.ts`,
  уже вызывалось раньше для `Notification` API) — без отдельной кнопки,
  тем же единственным запросом разрешения при заходе в админку.
- Настройка на сервере: `VAPID_PUBLIC_KEY`/`VAPID_PRIVATE_KEY` (сгенерировать
  раз и навсегда — `bunx web-push generate-vapid-keys`), опционально
  `VAPID_SUBJECT`. Без ключей — просто не работает, остальное не затронуто.

## Изображения в чате

- `POST /widget/upload` (токен посетителя) и `POST /admin/upload` (токен
  админа) — `multipart/form-data`, поле `file`. Только `image/jpeg`,
  `image/png`, `image/webp`, `image/avif`; максимум `MAX_UPLOAD_SIZE` (по
  умолчанию 10MB). Файл сохраняется в `UPLOAD_DIR` (по умолчанию `./uploads`)
  под случайным именем (UUID + расширение по mime-типу, не оригинальное имя —
  никаких коллизий и path traversal). Ответ: `{ url, type, name, size }`, где
  `url` — относительный путь вида `/uploads/<uuid>.<ext>`.
- `GET /uploads/:filename` отдаёт файл напрямую (`Bun.file`), без авторизации
  — как и сами ссылки на вложения в истории; имя файла случайное, подбором не
  найти.
- Вложение — не отдельная таблица, а 4 nullable-колонки на `messages`
  (`attachment_url`/`attachment_type`/`attachment_name`/`attachment_size`):
  одно сообщение — максимум один файл, этого достаточно по задаче. Отправка —
  обычное сообщение (WS или `POST /widget/messages`) с этими полями в теле,
  текст необязателен (можно отправить только картинку). Рассылается по WS
  как любое другое сообщение — виджет и админка просто рисуют `<img>`, если
  поле есть.
- Виджет: кнопка-скрепка рядом с полем ввода → превью с мини-спиннером во
  время загрузки → отправленная картинка — миниатюра в пузыре сообщения,
  тап/клик открывает полноэкранный просмотр (лайтбокс). Админка — тот же
  путь загрузки, но доступ к нему через меню «⋮» (см. ниже) плюс вставка из
  буфера обмена (`Ctrl+V`/`Cmd+V`) прямо в поле ввода — проверяет
  `clipboardData.items` на `image/*` и переиспользует тот же `handleFileSelect`,
  что и выбор файла.
- Админка, композер (`ChatWindow.tsx`), только на телефоне (`md:hidden`):
  эмодзи, прикрепить изображение и шаблоны ответов спрятаны за одной кнопкой
  «⋮» (как в Telegram) — список открывается попапом над полем ввода. На ПК
  (`md:` и шире) — три отдельные иконки в ряд, как было изначально. Хедер
  открытой беседы на телефоне — то же самое для назначить/скачать/удалить/
  закрыть: один «⋮» в хедере вместо тесного ряда кнопок, на ПК всё как было,
  инлайн.
- Админка, кнопка «✦ Спросить ИИ» в хедере (только ПК, `md:flex` в той же
  группе, что назначить/скачать/закрыть) — без платного API, на личном
  аккаунте оператора: по клику снимает скриншот видимой истории беседы
  (`html2canvas`, подгружается по клику отдельным чанком — не тянет ~200KB
  библиотеку в основной бандл), копирует картинку в буфер обмена
  (`navigator.clipboard.write`) и открывает `chatgpt.com` в новой вкладке.
  Вставить скриншот (`Ctrl+V`) в поле ввода ChatGPT оператор делает сам —
  программно вставить в чужой сайт из нашей страницы нельзя (cross-origin).
- Поле ввода (и в виджете, и в админке) — `textarea`, растёт вниз по мере
  текста (до `MAX_INPUT_HEIGHT`/`120px`, дальше — внутренний скролл), не
  скроллит содержимое вбок, как было бы с однострочным `input`. `Enter` —
  отправить, `Shift+Enter` — новая строка (не мешает IME-вводу, проверка
  `isComposing`).
- Автоочистка: раз в сутки (плюс сразу при старте сервера) вложения старше
  `ATTACHMENT_RETENTION_DAYS` (по умолчанию 3 дня) удаляются — файл с диска и
  сами поля вложения у сообщения; текст сообщения (если был) остаётся как есть.

## Аналитика

- `GET /admin/analytics/overview?from=&to=` — сводка за период (по умолчанию последние 7 дней): `total`/`open`/`closed` (по текущему статусу беседы), `avgFirstResponseSeconds` — среднее время от первого сообщения посетителя до первого сообщения админа в той же беседе, `respondedCount` — на скольких беседах основано среднее (`null`, если ни одна беседа ещё не получила ответ).
- `GET /admin/analytics/timeline?from=&to=&granularity=day` — количество новых бесед по дням; дни без бесед идут нулями, чтобы график не рвался. Пока поддерживается только `granularity=day`.
- `GET /admin/analytics/operators?from=&to=` — по каждому оператору: `assigned`/`closed`/`avgFirstResponseSeconds` за период. Операторы без бесед в периоде тоже показаны, с нулями. **Ограничение:** сообщения не хранят автора-оператора (только `sender: 'admin'`), поэтому время ответа считается по беседе в целом и приписывается текущему назначенному оператору, а не тому, кто фактически ответил.
- `from`/`to` — ISO-дата или дата-время; дата без времени в `to` считается включительно (до конца дня). Некорректный диапазон (`from` позже `to`) — 422.
- В админке: значок графика в шапке списка бесед → страница `Аналитика` (карточки с ключевыми цифрами, линейный график по дням на Recharts, таблица по операторам), селектор периода (7/30 дней или произвольный диапазон). `recharts` подключается отдельным чанком (`React.lazy`), чтобы не тянуть библиотеку в общий бандл тем, кто аналитику не открывает.

## Автотесты

Тесты API (`bun test`) поднимают приложение на случайном порту и работают с **отдельной** тестовой БД: перед каждым файлом они очищают таблицы, поэтому имя БД обязано содержать `test`, иначе тесты не запустятся.

```bash
cd vizaje-chat-api
docker exec vizaje-chat-db createdb -U postgres vizaje_chat_test     # один раз
export TEST_DATABASE_URL=postgres://postgres:dev@localhost:5433/vizaje_chat_test
DATABASE_URL=$TEST_DATABASE_URL bunx drizzle-kit push                # схема в тестовой БД
bun test
```

Покрыто: разделение токенов по `type`, rate-limit (вход, сессии, сообщения), REST и пагинация виджета, список бесед (сортировка, фильтры, счётчики, прочитанность), валидация WS-сообщений и `clientId` в ошибках, доставка сообщений и системных событий в реальном времени, Telegram-бот (навигация по меню не создаёт беседу, идемпотентность по `chat.id`, свободный текст после категории → беседа, снятие клавиатуры после нажатия, ответ оператора дублируется в чат, фото/картинка-документ вне режима поддержки игнорируется и доходит внутри него, ошибка скачивания файла, ответ оператора с вложением — `sendPhoto` по публичному URL, `/start` сбрасывает меню даже из режима поддержки, тема беседы приходит оператору системным сообщением один раз), загрузка изображений (валидация типа/размера, `/uploads/:filename`, вложение в WS- и REST-сообщении, подделанный `attachmentUrl` отбрасывается, автоочистка старых вложений), Web Push (подписка/отписка, идемпотентность по `endpoint`, уведомление на сообщение посетителя уходит на все сохранённые подписки), Instagram-канал (вебхук: верификация подписи по `X-Hub-Signature-256`, GET-рукопожатие, игнорирование `is_echo`, навигация по меню — общая с Telegram через `channels/`, тема беседы присылается заново при каждом новом обращении, ответ оператора — текст и фото), реакции на сообщения (422 на неподдерживаемый эмодзи, 404 на несуществующее сообщение, повторная реакция тем же оператором заменяет прежнюю, два оператора могут поставить разные реакции на одно сообщение, `/widget/messages` не отдаёт поле `reactions`).

В CI (`.github/workflows/ci.yml`) на каждый pull request: typecheck и тесты API с Postgres, lint и сборка админки, проверка синтаксиса виджета.

## Тест realtime без фронта

```bash
cd vizaje-chat-api
bun run src/scripts/test-realtime.ts
```

Прогоняет полный цикл: создание widget-сессии → admin login → оба WS коннектятся → обмен сообщениями в обе стороны. Полезно после любых правок WS-логики — быстрее, чем тестировать руками через браузер. Скрипт логинится под админом, которого вы создали через `create-admin.ts`; учётные данные берёт из переменных окружения:

```bash
ADMIN_EMAIL=admin@example.com ADMIN_PASSWORD=пароль bun run src/scripts/test-realtime.ts
```
