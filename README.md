# vizaje-chat

Standalone support-chat сервис для vizaje-nica.com (Jivo/Intercom-style). Не связан с legacy-кодом сайта — подключается через `<script>` виджет.

## Стек

- **Runtime:** Bun
- **Framework:** Elysia
- **БД:** PostgreSQL + Drizzle ORM
- **Auth:** JWT (отдельно для admin-операторов и анонимных widget-сессий)
- **Realtime:** WebSocket (нативный, через Elysia `.ws()`)

## Структура монорепо

```
vizaje-chat-api/      — API + WebSocket (Bun, Elysia, Drizzle)
  src/
    auth/             — admin login, JWT создание/проверка
    chat/             — сообщения, беседы, статус, rate-limit, публикация в WS
    widget/           — анонимные widget-сессии
    db/               — Drizzle schema + client
    routes/           — HTTP/WS роуты по доменам
    scripts/          — разовые скрипты (create-admin, test-realtime)
    config.ts         — переменные окружения
    index.ts          — сборка приложения
vizaje-chat-admin/    — веб-админка операторов (Vite + React)
vizaje-chat-widget/   — виджет для сайта (widget.js) и тестовая страница
```

## Локальный запуск

Нужны [Bun](https://bun.com) и Docker (для Postgres).

### 1. API (порт 3001)

```bash
cd vizaje-chat-api
bun install

# Postgres в докере
docker run --name vizaje-chat-db -e POSTGRES_PASSWORD=dev -p 5433:5432 -d postgres:16

# переменные окружения
cp .env.example .env    # затем впишите JWT_SECRET

# применить схему (таблицы и индексы)
bunx drizzle-kit push

# создать первого админа
bun run src/scripts/create-admin.ts admin@example.com пароль

# запуск
bun run src/index.ts
```

Проверка: `curl localhost:3001/health` возвращает `{"status":"ok"}`.

### 2. Админка (порт 5173)

```bash
cd vizaje-chat-admin
bun install
cp .env.example .env    # необязательно: по умолчанию API на http://localhost:3001
bun run dev
```

**Оповещения о новых сообщениях.** При заходе в админку браузер один раз спросит разрешение
на уведомления (если пользователь уже ответил — повторно не спрашивает). Новое сообщение
посетителя: звук (кнопка-колонка в шапке списка бесед выключает его), а если вкладка
неактивна — ещё и системное уведомление браузера (клик по нему фокусирует вкладку и
открывает беседу), бейдж с числом непрочитанных бесед на favicon и в `<title>`. Работает
только по HTTPS или на `localhost` — так требует Notification API.

### 3. Виджет (порт 8080)

```bash
cd vizaje-chat-widget
bun run dev --port 8080    # порт по умолчанию 8080
```

Откройте `http://localhost:8080`. Адрес API задаётся атрибутом `data-api` на теге `<script>` в `index.html`. Для встраивания на сайт:

```html
<script src="https://your-cdn/widget.js" data-api="https://chat.example.com"></script>
```

Необязательные атрибуты тега `<script>`:

| Атрибут | По умолчанию | Что делает |
|---|---|---|
| `data-theme` | `auto` | `auto` — системная тема посетителя, либо `light` / `dark` |
| `data-title` | `Поддержка Vizaje-Nica` | Заголовок панели и превью |
| `data-agent` | `Поддержка` | Подпись сотрудника под сообщениями |
| `data-lang` | `ru-RU` | Язык диктовки (речь в текст) |
| `data-greeting` | `Привет! 👋 Чем мы можем помочь?` | Приветствие в пустом чате |
| `data-subtitle` | `Наша команда также может помочь` | Подзаголовок под заголовком в шапке панели |
| `data-quick-replies` | — | Быстрые вопросы под приветствием через запятую, до 4 штук (запятую внутри вопроса использовать нельзя) |
| `data-privacy-url` | — | Ссылка на политику конфиденциальности; без неё строка под полем ввода не показывается |
| `data-privacy-text` | `Политикой конфиденциальности` | Текст ссылки в этой строке (вместе с `data-privacy-url`) |
| `data-position` | `bottom-right` | `bottom-right` или `bottom-left` |
| `data-z-index` | `999999` | `z-index` виджета |
| `data-offset-bottom` | `20` | Отступ снизу в px |
| `data-offset-right` / `data-offset-left` | `20` | Отступ от края в px; действует тот, что соответствует `data-position` |

**Приветствие и быстрые вопросы** — чисто фронтовый рендер: в БД не пишутся, в историю и аналитику не попадают и пропадают, как только в беседе появляется первое сообщение. Клик по кнопке отправляет её текст как обычное сообщение посетителя. Пример:

```html
<script src="widget.js" data-api="http://localhost:3001"
        data-greeting="Здравствуйте! Чем помочь?"
        data-quick-replies="Есть ли в наличии?,Сроки доставки,Как оформить возврат"
        data-position="bottom-left" data-offset-bottom="80"></script>
```

**Оформление** смоделировано по образцу Intercom: чёрный круглый лаунчер (иконка сообщения ⇄ шеврон при открытии/закрытии — независимо от темы сайта), квадратный тайл-«логотип» с сеткой из точек в шапке, двухстрочный заголовок (жирное название + серый подзаголовок), меню «⋯» справа (пока в нём только «Скачать историю» — замена отдельной иконки скачивания), единообразно скруглённые пузыри сообщений без «хвостика», составное поле ввода (textarea сверху, иконки эмодзи/диктовки и круглая кнопка отправки в строке снизу, всё в одной скруглённой рамке).

Позиция и слой читаются один раз при загрузке скрипта.

**Диктовка.** В поле ввода есть кнопка микрофона: речь превращается в текст по ходу разговора. Распознавание выполняет сам браузер (Web Speech API), поэтому серверная часть не задействована, а кнопка показывается только там, где браузер это умеет (Chrome, Edge, Safari; в Firefox её нет). Аудио при этом передаётся на серверы Google или Apple, о чём пользователь предупреждается при первом включении. Нужен HTTPS (на `localhost` работает и так), а браузер попросит доступ к микрофону.

Возвращающийся посетитель подключается к чату в фоне, поэтому на кнопке появляется бейдж непрочитанных, а над ней превью нового сообщения. Новым посетителям сессия создаётся только когда они открывают чат.

## Переменные окружения

### API (`vizaje-chat-api/.env`, шаблон в `.env.example`)

| Переменная | Обязательна | По умолчанию | Что делает |
|---|---|---|---|
| `DATABASE_URL` | да | — | Строка подключения к PostgreSQL |
| `JWT_SECRET` | да | — | Секрет подписи JWT; без него сервер не стартует |
| `ALLOWED_ORIGINS` | нет | `http://localhost:5173,http://localhost:8080` | Origins для CORS через запятую. Добавьте сюда домен сайта с виджетом и домен админки |
| `TRUST_PROXY` | нет | `false` | `true`, если API за reverse proxy: IP клиента берётся из `X-Forwarded-For` (нужно для rate-limit) |
| `PORT` | нет | `3001` | Порт HTTP/WS сервера |

### Админка (`vizaje-chat-admin/.env`)

| Переменная | Обязательна | По умолчанию | Что делает |
|---|---|---|---|
| `VITE_API_URL` | нет | `http://localhost:3001` | Адрес API; адрес WebSocket строится из него. Подставляется при сборке |
| `VITE_DICTATION_LANG` | нет | `ru-RU` | Язык диктовки (речь в текст) |

## WebSocket-протокол

Подключение: `ws://host/ws?token=...` (токен посетителя или админа). Клиент → сервер:

| Сообщение | Кто | Что делает |
|---|---|---|
| `{ text, replyToId?, clientId?, lang? }` | посетитель | Сообщение в свою беседу; `replyToId` — ответ на сообщение (только из этой же беседы); `lang` (`ru`/`ro`, по умолчанию `ru`) — язык автоответа бота, если `text` точно совпал с триггером |
| `{ conversationId, text, replyToId?, clientId? }` | админ | Сообщение в беседу, в том числе ответ на сообщение |
| `{ type: 'typing', conversationId? }` | оба | «Печатает» (не сохраняется, не чаще раза в секунду) |

Сервер → клиент — обычные сообщения (`{ id, conversationId, sender, text, createdAt, replyToId, replyTo }`, где `replyTo` — цитата `{ id, sender, text }` до 200 символов или `null`) и служебные события с полем `type`:

| `type` | Кому | Поля |
|---|---|---|
| `sent` | отправителю | `clientId`, `id`, `conversationId`, `createdAt` — подтверждение, серверные id и время |
| `error` | отправителю | `error`, `clientId` — сообщение отклонено (валидация, лимит) |
| `typing` | собеседнику | `from` (`visitor` / `admin`), `conversationId` |
| `read` | собеседнику и админам | `by` (`visitor` / `admin`), `conversationId`, `at` — «прочитано» |

«Прочитано» считается по серверному времени: оператор отмечает беседу прочитанной (`POST /admin/conversations/:id/read`), посетитель — когда виджет открыт (`POST /widget/read`); виджет читает состояние через `GET /widget/state`.

## Операторы и назначение бесед

Несколько операторов делят одну очередь бесед и могут назначать их друг на друга:

- `GET /admin/operators` — список операторов (`id`, `email`) для дропдауна назначения.
- `PATCH /admin/conversations/:id/assignee` — назначить (`{ "assigneeId": 2 }`) или снять назначение (`{ "assigneeId": null }`); публикует системное сообщение («Беседа назначена на …» / «Назначение беседы снято») по WS, как при смене статуса.
- `GET /admin/conversations?assignee=me` — только мои беседы; `?assignee=unassigned` — только без назначения (сочетается с `status`/`unread`).
- `GET /admin/conversations/counts` — добавлено поле `mine`.

В админке: дропдаун «Назначить» в шапке чата, фильтр «Мои» в списке бесед, инициалы назначенного оператора — бейджем на аватаре в списке. Операторы по-прежнему создаются CLI-скриптом `create-admin.ts` — отдельного UI/эндпоинта для создания операторов нет.

## Поиск по беседам

`GET /admin/conversations?q=текст` — ищет по всей истории переписки (не только по превью последнего сообщения) и по `sessionId` беседы, регистронезависимо, через `ILIKE %текст%` (полнотекстовый поиск для текущего масштаба избыточен). Сочетается с `status`/`unread`/`assignee`. Спецсимволы `%` и `_` в запросе экранируются, поэтому не ведут себя как маска.

В админке — поле поиска над фильтрами в списке бесед, debounce 350 мс, крестик или стирание текста возвращают обычный список с текущим фильтром; при пустом результате — «Ничего не найдено».

## Рабочий график и офлайн-статус

Вне рабочих часов виджет честно говорит посетителю, что сейчас никто не онлайн, а не создаёт ложное ощущение мгновенного ответа. Часовой пояс фиксирован — `Europe/Chisinau`.

- `GET /widget/status` — публичный (без авторизации): `{ online, nextOnlineAt, scheduleSummary }`. `nextOnlineAt` — ISO-время следующего открытия (или `null`, если график выключен целиком); `scheduleSummary` — человекочитаемая строка вроде `Пн–Пт 09:00–18:00, Сб 10:00–14:00`, склеивающая подряд идущие дни с одинаковыми часами.
- `GET/PUT /admin/settings/schedule` — только для админа. Тело/ответ: `{ timezone: "Europe/Chisinau", days: { mon: { enabled, start, end }, ..., sun: {...} } }` (`start`/`end` — `"HH:MM"`). Хранится в новой таблице `settings` (простой key-value, `jsonb`), без графика по умолчанию использует Пн-Пт 09:00–18:00. `PUT` проверяет формат времени и что начало раньше конца, при ошибке — 422 с текстом.
- В виджете: баннер над сообщениями при открытии чата, если `online: false`; отправка сообщений не блокируется — сообщение просто ждёт оператора.
- В админке: значок шестерёнки в шапке списка бесед открывает страницу графика (чекбокс + два `<input type="time">` на каждый день недели).

## Сезонная тема виджета

- `GET/PUT /admin/settings/theme` — только для админа. Тело/ответ: `{ theme: "classic" | "winter" }`, хранится в той же таблице `settings` под ключом `widgetTheme`, по умолчанию `classic`. `PUT` с неизвестным значением — 422.
- `GET /widget/config` — публичный (без авторизации), виджет вызывает его при загрузке страницы: `{ theme }`.
- Список тем держится в одном месте (`WIDGET_THEMES` в `settings/service.ts` на бэкенде и в `lib/api.ts` в админке) — добавить `spring`/`summer`/`autumn` в будущем можно дописав строку туда и ярлык в `ThemeSettings.tsx`, без переделки механизма.
- В виджете: при `theme: "winter"` поверх панели (но не поверх кликов — `pointer-events: none`) рисуются 8 падающих снежинок, CSS-анимация (падение + покачивание + вращение, `linear infinite`, разная длительность и фаза на каждую), приглушённая прозрачность, цвет снежинок берётся из CSS-переменной `--snow-color`, разной для светлой и тёмной темы, чтобы не сливаться с фоном ни в одной из них. При `classic` — эффектов нет.
- В админке: вкладка «Тема виджета» в настройках — выпадающий список + кнопка «Сохранить», по образцу вкладки рабочего графика.

## Шаблоны ответов (RU/RO)

- Таблица `canned_responses`: `id`, `title` (язык-нейтральный заголовок для списка и поиска), `text_ru`, `text_ro`, `created_at`.
- `GET/POST/PATCH/DELETE /admin/canned-responses` — только для админа. `POST` и `PATCH` проверяют, что все поля непустые, иначе 422; `PATCH` частичный — поля, которых нет в теле, не трогает.
- В настройках (значок шестерёнки → вкладка «Шаблоны ответов») — список, создание/редактирование одной формой (заголовок + текст RU + текст RO), удаление.
- В `ChatWindow` — кнопка рядом с эмодзи открывает панель шаблонов: табы RU/RO (выбор языка запоминается в `localStorage` между сессиями), фильтр по заголовку на фронте, клик вставляет текст выбранного языка в позицию курсора, не отправляя — как вставка эмодзи.

## FAQ-бот с автоответами

- Таблица `bot_responses`: `id`, `trigger_text` (точный текст вопроса/quick-reply кнопки), `answer_ru`, `answer_ro`, `created_at`. Отдельная сущность от `canned_responses` — назначение разное: шаблоны вставляет оператор вручную, автоответы бот отправляет сам.
- `GET/POST/PATCH/DELETE /admin/bot-responses` — только для админа, та же схема валидации/ошибок, что у шаблонов ответов.
- В WS: когда посетитель отправляет сообщение, **точно** совпадающее с `trigger_text` одного из автоответов, сразу создаётся сообщение с `sender: 'bot'` и соответствующим `answer_ru`/`answer_ro` (по полю `lang` в сообщении посетителя) — без участия оператора. Не совпало — обычное сообщение ждёт оператора как раньше. Сообщения от админа триггер не проверяют. Эскалации на «позвать оператора» пока нет — добавится отдельным шагом при необходимости.
- Виджет передаёт `lang` в каждом сообщении (`ro`, если `data-lang` начинается с `ro`, иначе `ru`), поэтому клик по кнопке из `data-quick-replies`, чей текст совпадает с `trigger_text` в базе, даёт мгновенный автоответ бота вместо обычной отправки оператору — без отдельной логики на стороне виджета, кнопка просто шлёт текст как обычное сообщение.
- В настройках (значок шестерёнки → вкладка «Ответы бота») — список, создание/редактирование (триггер + ответ RU + ответ RO), удаление.
- В списке бесед и в окне чата сообщения от бота помечены иконкой робота (по аналогии с отрисовкой `sender: 'system'`).

## Экспорт переписки

- `GET /widget/export` (токен посетителя) и `GET /admin/conversations/:id/export` (токен админа, любая беседа по id) отдают всю историю беседы простым текстом: `Content-Type: text/plain; charset=utf-8`, `Content-Disposition: attachment; filename="conversation-{id}.txt"`.
- Формат: заголовок `Беседа #{id} — экспортировано {дата время}`, затем по одной строке на сообщение в хронологическом порядке — `[дата время] Отправитель: текст` (`Посетитель` / `Оператор` / `Бот`); системные сообщения (смена статуса, назначение) — отдельной строкой `--- текст ---` без таймштампа, как они есть в истории. Дата/время — в таймзоне `Europe/Chisinau`, как в рабочем графике.
- В виджете: иконка скачивания в шапке панели рядом с крестиком закрытия. В админке: кнопка-иконка в шапке `ChatWindow` рядом с «Назначить»/«Закрыть». Оба скачивают файл через `fetch` + `Blob` (эндпоинт требует авторизацию, прямая ссылка не сработает); имя файла берётся из `Content-Disposition`.

## Проактивное приглашение (виджет)

Полностью фронтовая фича виджета, без бэкенда — отключена по умолчанию.

- `data-proactive-message` — текст приглашения; без него фича выключена.
- `data-proactive-delay` — задержка до показа, в секундах (по умолчанию 20).
- Пузырь всплывает рядом с кнопкой чата через заданную задержку, но только если чат ещё не открывали в этой вкладке и у посетителя нет `widget_token` в `localStorage` (то есть это анонимный визит, а не вернувшийся собеседник). Клик по тексту открывает панель чата; крестик закрывает пузырь и пишет флаг в `sessionStorage` — до конца текущей вкладки больше не покажется, в новой вкладке/сессии сработает заново.
- Использует тот же слот над кнопкой чата, что и превью нового сообщения (`.toast`) — одновременно они не показываются по построению (превью требует уже идущей беседы, приглашение — наоборот, её отсутствия), и учитывает `data-position`/`data-offset-*`.

## Аналитика

- `GET /admin/analytics/overview?from=&to=` — сводка за период (по умолчанию последние 7 дней): `total`/`open`/`closed` (по текущему статусу беседы), `avgFirstResponseSeconds` — среднее время от первого сообщения посетителя до первого сообщения админа в той же беседе, `respondedCount` — на скольких беседах основано среднее (`null`, если ни одна беседа ещё не получила ответ).
- `GET /admin/analytics/timeline?from=&to=&granularity=day` — количество новых бесед по дням; дни без бесед идут нулями, чтобы график не рвался. Пока поддерживается только `granularity=day`.
- `GET /admin/analytics/operators?from=&to=` — по каждому оператору: `assigned`/`closed`/`avgFirstResponseSeconds` за период. Операторы без бесед в периоде тоже показаны, с нулями. **Ограничение:** сообщения не хранят автора-оператора (только `sender: 'admin'`), поэтому время ответа считается по беседе в целом и приписывается текущему назначенному оператору, а не тому, кто фактически ответил.
- `from`/`to` — ISO-дата или дата-время; дата без времени в `to` считается включительно (до конца дня). Некорректный диапазон (`from` позже `to`) — 422.
- В админке: значок графика в шапке списка бесед → страница `Аналитика` (карточки с ключевыми цифрами, линейный график по дням на Recharts, таблица по операторам), селектор периода (7/30 дней или произвольный диапазон). `recharts` подключается отдельным чанком (`React.lazy`), чтобы не тянуть библиотеку в общий бандл тем, кто аналитику не открывает.

## Автотесты

Тесты API (`bun test`) поднимают приложение на случайном порту и работают с **отдельной** тестовой БД: перед каждым файлом они очищают таблицы, поэтому имя БД обязано содержать `test`, иначе тесты не запустятся.

```bash
cd vizaje-chat-api
docker exec vizaje-chat-db createdb -U postgres vizaje_chat_test     # один раз
export TEST_DATABASE_URL=postgres://postgres:dev@localhost:5433/vizaje_chat_test
DATABASE_URL=$TEST_DATABASE_URL bunx drizzle-kit push                # схема в тестовой БД
bun test
```

Покрыто: разделение токенов по `type`, rate-limit (вход, сессии, сообщения), REST и пагинация виджета, список бесед (сортировка, фильтры, счётчики, прочитанность), валидация WS-сообщений и `clientId` в ошибках, доставка сообщений и системных событий в реальном времени.

В CI (`.github/workflows/ci.yml`) на каждый pull request: typecheck и тесты API с Postgres, lint и сборка админки, проверка синтаксиса виджета.

## Тест realtime без фронта

```bash
cd vizaje-chat-api
bun run src/scripts/test-realtime.ts
```

Прогоняет полный цикл: создание widget-сессии → admin login → оба WS коннектятся → обмен сообщениями в обе стороны. Полезно после любых правок WS-логики — быстрее, чем тестировать руками через браузер. Скрипт логинится под админом, которого вы создали через `create-admin.ts`; учётные данные берёт из переменных окружения:

```bash
ADMIN_EMAIL=admin@example.com ADMIN_PASSWORD=пароль bun run src/scripts/test-realtime.ts
```
